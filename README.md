# IROPS Disruption Memory Agent

An operational-memory agent for airline irregular-operations (IROPS) desks.
Every resolved disruption becomes retrievable precedent that improves the
handling of the next one.

Built for the **CockroachDB × AWS Hackathon — "Build with Agentic Memory."**

## The problem

When a flight is disrupted, ops staff must decide fast: who gets rebooked
where, which misconnecting passengers are recoverable, who needs priority
handling. Every disruption is handled largely from scratch. The institutional
knowledge of *"we saw this exact shape of disruption last month and here is
what actually worked"* lives in people's heads and evaporates with staff
turnover.

Traditional systems store **records**. They do not store **judgement**.

## What this does

```
new disruption arrives
  → agent embeds a structured summary of the case
  → semantic search over past cases in CockroachDB (vector index)
  → agent retrieves precedent + the outcomes those precedents produced
  → agent reads current structured state (passengers, connections, capacity)
  → agent proposes a concrete action plan (structured, reviewable actions)
  → human approves / edits / rejects
  → outcome is written back as new memory, embedded, becomes precedent
```

**Why this is not a chatbot:** the agent proposes typed actions against state,
records the human's decision, and its future behaviour changes because of what
it recorded. Memory is the product, not a feature.

**Rejected proposals are memory too.** An agent that records what humans
overruled is more useful than one that only records its successes — the
overrule is the strongest signal in the dataset.

### Non-goals

- Not a rebooking engine. It recommends; it integrates with no real
  reservation system.
- Not a chat interface with an airline theme pasted on.
- Not a pretty UI. Minimal, legible, functional.

## Data provenance

**All data in this repository and its demo is synthetic**, generated by a
script in this repo. There is no real passenger data, no real booking
references, no real customer names. The domain framing uses only generic,
publicly documented airline-operations concepts (delays, misconnections,
rebooking, priority handling).

```
   └─ vector index on case + resolution embeddings
        ▲
        └── CockroachDB Managed MCP Server (read-only) — analyst query path
```

### The point of CockroachDB here

Vectors and transactional rows live in **one** system. There is no ETL job and
no consistency gap between "what the agent remembers" and "what actually
happened" — the embedding write and the state write commit in the same
transaction. A separate vector database would reintroduce exactly the drift
this design exists to avoid.

### Running without any live services

The app is designed to boot with no cloud credentials at all. Set:

```
EMBEDDING_PROVIDER=fake
LLM_PROVIDER=fake
```

and the agent uses deterministic local stand-ins instead of Bedrock. This
keeps local development free, offline, and reproducible. The fake providers
are **not** a fallback path in production — if a real provider is configured
and fails, the failure surfaces rather than being silently swallowed.

## Configuration

All configuration is via environment variables — see
[.env.example](.env.example) for the annotated list.

No credentials, connection strings, or API keys are committed to this
repository. In deployment, secrets are supplied as Lambda environment
variables sourced from AWS Secrets Manager.
