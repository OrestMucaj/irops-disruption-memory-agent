## 2. The product

**IROPS Disruption Memory Agent** — an operational-memory agent for airline irregular-operations desks.

### The problem

When a flight is disrupted (delay, cancellation, diversion), ops staff must decide fast: who gets rebooked where, which misconnecting passengers are recoverable, who needs priority handling. Every disruption is handled largely from scratch. The institutional knowledge of "we saw this exact shape of disruption last month and here's what actually worked" lives in people's heads and evaporates with staff turnover. Traditional systems store *records*; they don't store *judgement*.

### The agent

An agent whose memory **compounds**: each resolved disruption becomes retrievable precedent that improves the handling of the next one.

The core loop, and the thing the demo must make visible:

```
new disruption arrives
  → agent embeds a structured summary of the case
  → semantic search over past cases in CockroachDB (vector index)
  → agent retrieves precedent + the outcomes those precedents produced
  → agent reads current structured state (passengers, connections, capacity)
  → agent proposes a concrete action plan (not prose — structured, reviewable actions)
  → human approves / edits / rejects
  → outcome is written back as new memory, embedded, and becomes precedent
```

**Why this is not a chatbot:** the agent proposes typed actions against state, records the human's decision, and its future behaviour changes because of what it recorded. Memory is the product, not a feature.

### Explicit non-goals

- Not a rebooking engine. It recommends; it does not integrate with any real reservation system.
- Not a chat interface with an airline theme pasted on.
- Not a pretty UI. Minimal, legible, functional.

## 4. Data model

Verify exact vector column/index syntax against current CockroachDB docs before writing the DDL. Shape:

- **`disruption_cases`** — `id`, `flight_no`, `origin`, `destination`, `scheduled_dep`, `actual_dep`, `delay_minutes`, `cause` (weather / technical / crew / atc / knock-on), `aircraft_type`, `pax_count`, `misconnect_count`, `priority_pax_count`, `status` (open / planned / resolved), `created_at`
- **`passengers`** — `id`, `case_id`, `pax_ref` (synthetic), `priority_tier`, `onward_flight`, `connection_minutes`, `connection_status` (safe / at_risk / missed), `rebooked_to`, `special_handling`
- **`case_embeddings`** — `case_id`, `summary_text`, `embedding` (vector), `embedded_at`
  - `summary_text` is a deterministic, generated natural-language digest of the case's structured fields. Generating this well is high-leverage: it is what semantic similarity actually operates on.
- **`proposed_actions`** — `id`, `case_id`, `action_type` (rebook / prioritise / hotel / notify / escalate), `target_pax_ref`, `payload` (JSONB), `rationale`, `precedent_case_ids` (array), `confidence`, `status` (proposed / approved / rejected / edited), `created_at`
- **`resolutions`** — `id`, `case_id`, `actions_taken` (JSONB), `outcome_notes`, `outcome_rating`, `resolved_at`, `embedding` (vector)
- **`agent_runs`** — `id`, `case_id`, `model_id`, `prompt_tokens`, `completion_tokens`, `latency_ms`, `retrieved_case_ids`, `error`, `created_at`
  - This table is the observability story. It directly serves the "Production Readiness" criterion. Do not skip it.

**Design note to honour:** the whole point of CockroachDB here is that vectors and transactional rows live in **one** system — no ETL, no consistency gap between "what the agent remembers" and "what actually happened." Make sure the README says this explicitly and that the code demonstrates it (embedding write and state write in the same transaction where sensible).

## 5. Agent implementation

### 5.1 Retrieval

1. Build `summary_text` from the new case's structured fields.
2. Embed via Bedrock.
3. Vector search `case_embeddings` for top-k (k=3..5) similar historical cases.
4. Join through to those cases' `resolutions` — **retrieve what was done and how it turned out**, not just the similar case. Precedent without outcome is useless.
5. Apply a hard filter alongside semantic similarity (e.g. only `status = 'resolved'`). Hybrid structured + semantic retrieval in one query is exactly the differentiator to show off.

### 5.2 Reasoning

Single Bedrock call with a strict system prompt:
- Inputs: current case state, misconnecting passenger list, retrieved precedents + outcomes.
- Output: **strict JSON** — an array of proposed actions, each with `action_type`, `target_pax_ref`, `rationale`, `precedent_case_ids`, `confidence`. No prose outside the JSON.
- Parse defensively. Validate against a schema (zod or equivalent). On parse failure, retry once with the error fed back, then fail gracefully with a visible error state — never crash, never silently show nothing.

### 5.3 Write-back

- Approved/edited/rejected actions all persist, with which precedents were cited.
- On case resolution: write `resolutions` row, generate + store its embedding. **The rejected proposals are memory too** — an agent that records what humans overruled is more interesting than one that only records successes. Mention this in the README; it's a genuine originality point.

### 5.4 Guardrails (Production Readiness)

- No action is ever auto-executed. Human approval is structurally required.
- Rate-limit / cap Bedrock calls per case.
- Timeouts on DB and model calls with sane fallbacks.
- Every agent run logged to `agent_runs` including failures.
- Parameterised queries only.

- 2026-07-29 (session 2, M2 complete) — **Synthetic history seeded. Retrieval measurably beats chance. M2 exit criterion met.**

  84 cases (80 resolved + 4 live), 1,513 passengers, 84 case embeddings, 80 resolutions. Fully deterministic from a seed — same input, same dataset, same UUIDs, on any machine. `npm run seed -- --reset`.

  **The dataset contains a deliberate, learnable pattern.** A corpus of random rows would let retrieval look like it works while proving nothing. So the generator encodes a legible playbook — the right response is driven mostly by cause, severity, and above all the *hour of day*, because a three-hour delay at 07:00 is an inconvenience and the same delay at 21:00 means hotels — then deviates from it in 28% of cases and records the worse outcome that followed. 14 of 80 resolutions are rated 1–2 with notes explaining what went wrong. **Negative precedent is the point**: an agent that can retrieve "this was tried here and it backfired" is more useful than one that only sees successes.

  **Exit criterion, measured rather than eyeballed.** Three hand-picked examples prove nothing, so: leave-one-out over all 80 resolved cases, scored against the baseline from the corpus's own class distribution (assuming a uniform baseline would have flattered the result).

  | Axis | Retrieved | Chance | Lift |
  | --- | --- | --- | --- |
  | same cause | 71.3% | 21.3% | 3.34× |
  | same severity | 65.0% | 35.6% | 1.83× |
  | same recovery window | 70.5% | 27.7% | 2.54× |

  This is the **fake** lexical embedder. Bedrock should improve on it, so this is a floor rather than a ceiling — and it means the retrieval path is developable and demo-able with no AWS account at all.

  **`summary_text` design, since M2 says everything downstream depends on it:** lead with what makes cases operationally alike (cause, severity, station type, recovery window) and keep flight number and airport pair brief, or every LHR departure looks like every other one. Emit the bucket word *and* the number — "187 minutes" and "192 minutes" are operationally identical and lexically unrelated, so numbers alone are nearly useless to an embedding. Fully deterministic; a summary that drifts silently invalidates every stored vector.

Embeddings are still written one row at a time per NOTES §1.9. - 2026-07-29 (session 2, M3 structural) — **Agent loop runs end-to-end and its failure paths are tested. Only the Bedrock call is missing.**

  `npm run agent` executes the full loop against a seeded case: retrieve precedent → build prompt → model → parse → validate → ground → persist proposals → log the run. Observed on a live case: 5 precedents retrieved (4 of 5 same-cause, one flagged as having gone badly), 4 grounded actions persisted as `proposed`, `agent_runs` row written with token counts, latency and retrieved case IDs.

  **Refactor first, to close a silent-failure hole.** `summary_text` generation lived inside `src/seed/`, so a live case would have been summarised by different code from the seeded corpus — similarity would have quietly collapsed with nothing erroring. Moved to `src/domain/` behind structural `CaseFacts`/`PassengerFacts` interfaces that both the generator and a database row satisfy. One code path, guaranteed.

  **The guardrail that matters most is grounding, not schema validation.** A model can emit perfectly valid JSON citing a precedent that was never retrieved, or naming a passenger who is not on the flight. Schema validation passes that straight through. So the two are separated, and treated asymmetrically: a **fabricated citation** is stripped but the action survives (the advice may still be sound, it just is not supported by the case it claims); a **fabricated passenger reference** kills the whole action (there is no safe way to partially honour rebooking someone who does not exist). For an agent whose pitch is "it cites its precedents", an uncheckable citation is worse than none — it looks like evidence.

  **Failure paths are tested, not asserted** — `npm run check:guardrails`, 5/5 passing: unparseable response degrades gracefully with a retry; valid-JSON-wrong-shape degrades gracefully; fabricated citation stripped with the action surviving; fabricated passenger reference drops the action while its safe sibling survives; well-formed response persists. Every scenario also asserts the failure reached `agent_runs`, and the test cleans up every row it creates.

  **Badly-rated precedents are given to the model and labelled as warnings.** The obvious move is to show only successes; that discards the most informative rows in the corpus. 14 of 80 seeded resolutions went wrong, and why they went wrong is exactly the institutional knowledge the system exists to retain.

  **Added `heuristic` LLM provider** — a hand-written decision tree, emphatically not a language model. It exists so the loop and the M4 UI are developable offline at zero cost, and as a baseline Bedrock has to beat. Loudly labelled in code, in `.env.example`, and in CLI output. `EMBEDDING_PROVIDER` and `LLM_PROVIDER` now have separate value lists since `heuristic` is meaningless for embeddings.

  **Blocked** — `BedrockLLMProvider` is still a stub. It needs AWS IAM keys (the dev user + scoped Bedrock policy). Nothing else waits on it.

  **Next: M4 — frontend and deploy.** Three views, Lambda, S3, public URL. Can be built entirely against the heuristic provider and swapped to Bedrock when keys arrive.

- 2026-07-29 (session 2, M3 complete) — **Running on real Bedrock end to end. And the switch exposed a serious flaw in `summary_text` that only real embeddings could reveal.**

  IAM user created with a policy granting exactly `bedrock:InvokeModel` in one region. Smoke tests first, per §1.2, then implementation.

  **Bedrock verified (NOTES §4A):** Titan V2 returns 1024 dimensions at L2 norm 1.000000 — confirming it normalizes by default, which retroactively justifies the fake provider doing the same. Related text scores cosine 0.575 against 0.044 for unrelated. No throttling on first call, so **Service Quota is not zero on a new account** — closing the last doubt from §6.6.

  **Model IDs were probed, not chosen from a page**, because §4.3 records AWS's own docs contradicting themselves on one. All three Nova models work in us-east-1 and return strict JSON; Anthropic returns ResourceNotFound pending the one-time use-case form. Picked `amazon.nova-lite-v1:0` over the probe's latency-based recommendation of Micro: all three answer in ~700ms, and multi-document reasoning over precedent is the wrong place to economise on model size when the difference is fractions of a cent.

  **Converse API, not InvokeModel** — one request shape across all models, so swapping model is a config edit, and it reports token usage uniformly. `agent_runs` now records **real** token counts (1,930 / 937 on a live run) rather than estimates. `stopReason: max_tokens` raises its own error, since a retry would truncate identically and "not valid JSON" would be a misleading thing to log.

  **The finding that mattered.** Switching to real embeddings made retrieval *worse*, and the recovery-window signal — the most decision-relevant fact about a disruption — fell to **27.8%, exactly chance**, from 70.5% with the lexical fake.

  Cause: `summary_text` had been accidentally tuned to token overlap. The window sat at sentence 5 of 6, behind a sentence of flight number, route and aircraft that is near-identical across all 84 cases. Lexical matching does not care about position or dilution. A semantic model does.

  Fix: lead with an operational-signature sentence carrying every discriminator, restate the window's consequence in its own sentence, demote flight and route to last. Window recovered to **42.8% (1.54× lift)** and all three axes pass. Cause gave up some ground (61.3% → 56.0%) — a real trade, taken deliberately.

  ⚠️ **The fake embedder still scores higher on this benchmark, and that does not mean it is better.** The metric scores agreement on labels that are literally words in the text, which is what lexical matching is unbeatable at. Titan generalises to paraphrases the fake cannot see. The benchmark flatters the fake by construction. Worth remembering before quoting either number at a judge.

  **Guard added:** `checkEmbeddingModelConsistency` refuses to run when stored vectors came from a different model than the configured provider. Flipping `EMBEDDING_PROVIDER` on a seeded database would otherwise return confident, ordered, meaningless results with nothing erroring — the sharpest footgun in the system, and the reason `case_embeddings.model_id` exists.

  **Verified after the switch:** all 5 guardrail scenarios still pass; M2 exit criterion re-met on real embeddings; agent runs end to end producing 4 grounded actions citing real precedent IDs and real passenger references.

  **Quality note for M6:** Nova Lite's rationales are formulaic and it cites all five precedents indiscriminately on the case-level action. Prompt tuning, or Nova Pro, is a cheap polish item — not a blocker.

  **Three deployment bugs worth recording, because each looked like something else:**

  1. **403 on the Function URL despite a textbook-correct resource policy.** AWS changed this in **October 2025**: "new function URLs will require both `lambda:InvokeFunctionUrl` **and** `lambda:InvokeFunction` permissions", and the docs are explicit that missing the second gives 403 "even if the function URL uses the `NONE` auth type". Almost every example online shows only the first. The policy read as perfectly correct — Allow, Principal `*`, right condition — and still failed, with nothing indicating which half was missing. The console and SAM add both automatically; the CLI does not.

  2. **Duplicate CORS headers.** The Lambda handler set CORS headers *and* the Function URL's `--cors` config added them, producing two `Access-Control-Allow-Origin` headers. The spec permits exactly one, so browsers rejected every response with an opaque "Failed to fetch" — while curl, which does not enforce CORS, reported a healthy 200. Fixed by making the Function URL own CORS in deployment and the dev server own it locally.

  3. **Two PowerShell traps, one a repeat.** `Set-Content -Encoding utf8` emits a BOM in PowerShell 5.1 and the AWS CLI cannot parse JSON starting with one; switched to `[System.IO.File]::WriteAllText`. And redirecting native stderr with `2>&1` under `ErrorActionPreference=Stop` throws before `$LASTEXITCODE` can be read — the same trap already fixed once in the provisioning script, reintroduced here.

  **Security incident, recorded honestly.** The BOM parse failure made the AWS CLI echo the entire environment payload — including `DATABASE_URL` with its password — to the console. Passing it by file reference was meant to keep it off command lines; it did not anticipate the CLI printing the file back on a parse error. The script now routes all AWS output through a redactor that masks connection strings. **The database password was exposed and should be rotated.**
